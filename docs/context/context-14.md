14. ЧТО НЕ НАДО ПРЕДЛАГАТЬ
Список конкретный. Если тема в этом списке — не предлагать. Не «обсудить», не «а может», не «в порядке эксперимента».

14.1. Фреймворки и их компоненты
Laravel

Symfony (целиком)

Illuminate/ компоненты* (даже по одному: Eloquent, Blade, Container, Support)

CodeIgniter

Yii

CakePHP

Laminas / Zend

Slim

Phalcon

Почему: Evo — сам себе фреймворк. Тянем библиотеки, не фреймворки.

14.2. Шаблонизаторы
Twig

Blade

Smarty

Mustache

Latte

Plates

Volt

Почему: в Evo шаблоны — это чанки с [+placeholder+]. Просто и понятно. Шаблонизатор — это лишний слой.

14.3. ORM
Eloquent

Doctrine ORM

Propel

Cycle ORM

RedBeanPHP

Почему: Evo работает с БД через $modx->db (обёртка над mysqli). Для нового кода — тонкий слой над PDO. ORM — оверкилл.

14.4. SPA и фронтенд-фреймворки для админки
Vue

React

Angular

Svelte

Alpine.js (для крупных компонентов)

Livewire

Inertia.js

Почему: управление админкой — классический серверный рендеринг + формы. JS — минимально. Исключение — автокомплит поиска, drag&drop сортировки, живой предпросмотр.

14.5. Тяжёлые DI-контейнеры
Laravel Container

Symfony DI

PHP-DI

Auryn

Почему: если очень нужен контейнер — минимальный, свой, 50 строк. И только в src/, не в сниппетах.

14.6. AJAX-first архитектура
Все модули через JSON-API.

Фронт дёргает эндпоинты, бэкенд отвечает JSON.

Прогрессивные веб-приложения (PWA).

Оффлайн-режим.

Почему: классические POST-формы + redirect — по умолчанию. AJAX — точечно, где без него UX страдает.

Отказались. Не обсуждаем.

14.8. SaaS-конструктор магазинов

14.10. Вкладки в Конфигурации Evo через JS-инжект
Не работает. UI конфигурации Evo 1.4 строится из PHP-файлов админки (manager/actions/mutate_settings/tab*.inc.php), не из БД. Вкладки там не появятся через JS.

Правильный путь: отдельный модуль (как seoVolo Settings).

14.11. OnSiteSettingsRender
Не работает для наших задач. Событие вызывается, но вставляет только в свою вкладку «Сайт». Для новых полей непригодно.

14.12. regClientCSS() / regClientScript() в форме документа
Не работает надёжно. Только $modx->event->output() или echo в контексте ManagerManager.

14.13. Laravel-паттерны в Evo
Schema::create(...)

Blueprint

migrations как в Laravel

Model::where(...)

Facades

ServiceProvider

В Evo ничего из этого нет. Не тащить.

14.14. Что можно предложить, но с оговоркой
Composer — да, для библиотек. Не для фреймворков.

PSR-4 — да, в src/. Не в сниппетах.

PDO — да, в новом коде. Старый DBAPI остаётся.

PSR-3 (log) — да.

PSR-14 (events) — да, новый слой. Старый invokeEvent остаётся.

PSR-7 / PSR-15 (HTTP) — да, для нового API (если понадобится).

14.15. Если сомневаешься
Перед предложением спроси себя:

Это ломает простоту Evo? Если да — не предлагать.

Это тянет фреймворк/шаблонизатор/ORM? Если да — не предлагать.

Это в сниппете/плагине/чанке? Если да — там только простой PHP.

Это в src/? Тогда можно, но с оговорками из частей 12–13.

Это замена существующего рабочего решения? Тогда сначала доказать, что новое лучше.
