13. АРХИТЕКТУРНЫЕ ПРИНЦИПЫ ФОРКА
13.1. Что делаем
13.1.1. Composer
composer.json в корне репо.

PSR-4 автозагрузка для src/.

vendor/ — в .gitignore, не коммитится.

Библиотеки — только нужные (см. часть 12.2).

13.1.2. Стандарты кода
PSR-12 — форматирование.

declare(strict_types=1) — в новом коде (src/).

Типизация аргументов и возвратов.

PHP 8.4+ features: readonly, enums, attributes.

Старый код Evo не трогаем — там свой стиль, и это нормально.

13.1.3. PSR-интерфейсы — точечно
PSR	Для чего	Где
PSR-3	Логирование	src/Log/ — замена logEvent в новом коде
PSR-11	Контейнер	Минимальный свой, если понадобится
PSR-14	Event dispatcher	src/Events/ — новый слой (старый invokeEvent остаётся)
PSR-7	HTTP-запросы/ответы	src/Http/ — для нового API
PSR-15	Middleware	src/Http/Middleware/ — для нового роутинга
Без фанатизма. Только там, где реально нужно. Старый код не переводим на PSR.

13.1.4. БД
PDO — в src/Database/ для нового кода.

Prepared statements — везде в новом коде.

Старый DBAPI (mysqli) — остаётся для extras (обратная совместимость критична).

Миграции — свой тонкий слой, не Laravel Schema.

13.1.5. Архитектура
src/ — корень нового кода.

Namespace Vololution\... — PSR-4.

Разделение: Core/, Modules/, Admin/, Http/, Database/, Log/, Events/.

Старые файлы Evo (manager/, assets/) не переезжают. Работают как есть.

13.1.6. Admin UI
Постепенный уход от manager/actions/*.php с eval-инклюдами к контроллерам и шаблонам.

Но без Twig/Blade. На простом PHP + HTML.

Точка входа модуля — простая (include), внутри — нормальные классы.

13.2. Политика апстрима
13.2.1. Основные правила
upstream = evocms-community/evolution.

Мержим не каждый релиз. Только:

security-фиксы — обязательно,

крупные багфиксы — по ситуации,

новые фичи — только если нужны нам.

Не гоняемся за каждым релизом.

Мерж — в отдельной ветке merge/upstream-YYYY-MM.

Тест на vol.test — только потом в main.

После мержа — синхронизация docs/patches-manifest.md (реестр отличий).

13.2.2. Пошаговый процесс мержа
text
1. git fetch upstream
2. git checkout -b merge/upstream-2026-11
3. git merge upstream/1.4.x
4. Разрешаем конфликты — сверяясь с docs/patches-manifest.md
5. Тест на vol.test
6. git checkout main
7. git merge merge/upstream-2026-11
8. git push
9. git tag v1.4.37-vololution-N
10. git push --tags
11. Обновить CHANGELOG.md, patches-manifest.md, CONTEXT.md
13.2.3. Что мержим в первую очередь
Security-фиксы — всегда:

Из github.com/extras-evolution/security-fix.

Из релизов CE с пометкой security.

Из коммитов evocms-community/evolution без релиза.

Крупные багфиксы — по ситуации:

Если касаются ядра или CSRF — берём.

Если касаются только узких сценариев — смотрим по обстоятельствам.

Новые фичи — только если нужны:

Например, поддержка PHP 8.6, новая версия редактора — да.

Косметические улучшения интерфейса — нет.

13.2.4. Что НЕ мержим
Изменения, которые ломают наши патчи ядра.

Изменения, которые конфликтуют с философией простоты.

Изменения, которые тянут за собой новые зависимости (фреймворки, шаблонизаторы).

Косметические правки без функциональной ценности.

13.2.5. Обработка конфликтов
Если конфликт в наших 13 патчах ядра:

Взять версию апстрима.

Проверить, устранена ли причина нашего патча (например, E_STRICT уже убран — тогда наш патч не нужен).

Если причина осталась — наложить патч заново.

Обновить docs/patches-manifest.md.

Если конфликт в install/ или Store installer:

Патчить оба комплекта (см. часть 4).

Если конфликт в SEO-пакете или Store:

Они не зависят от ядра CE. Не сломаются при обновлении.

Если апстрим тронул файл из assets/ (CodeMirror, ManagerManager) — заново наложить патчи на них (CHANGELOG 2.6, 2.7).

13.3. Что НЕ делаем
Не форкаем evolution-cms (старая ветка). Только evocms-community/evolution.

Не следим за официальным evo.im. Он заморожен, только security fixes.

Не тянем Illuminate/*, Symfony/* компоненты. Даже по одному.

Не переписываем ядро с нуля. Постепенная модернизация.

Не отказываемся от обратной совместимости с extras. Это критично.

Не вводим AJAX-first архитектуру. Классические формы по умолчанию (см. часть 12).

13.4. Ветки в репозитории
Ветка	Назначение
main	Стабильная. Рабочая. Готовая к развёртыванию.
dev	Разработка новых фич. Промежуточная.
merge/upstream-YYYY-MM	Временная, для мержа апстрима.
feature/<название>	Для крупных фич (магазин, авторизация).
fix/<название>	Для багфиксов.
Правило: в main — только то, что протестировано на vol.test и на проде.

13.5. Теги
v1.4.37-vololution — точка форка (первый коммит).

v1.4.37-vololution-N — после каждого мержа апстрима (N = 1, 2, 3...).

v1.5.0-vololution — когда накопятся наши крупные фичи (магазин, авторизация).
