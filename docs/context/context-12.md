## 12. ФИЛОСОФИЯ ПРОСТОТЫ: ЗАПРЕЩЕНО / РАЗРЕШЕНО / ПРАКТИКА

Продолжение части 11. Здесь — конкретные списки.

### 12.1. Что запрещено окончательно

#### Шаблонизаторы

- **Twig**
- **Blade**
- **Smarty**
- **Mustache**
- **Latte**
- **Plates**

**Нет.** Только чанки Evo.

#### Фреймворки

- **Laravel**
- **Symfony**
- **CodeIgniter**
- **Yii**
- **CakePHP**
- **Laminas / Zend**

**Нет.** Evo сам себе фреймворк.

#### ORM

- **Eloquent**
- **Doctrine**
- **Propel**

**Нет.** Свой тонкий слой над PDO для нового кода, `$modx->db` — для старого.

#### SPA на фронте (для управления)

- **Vue**
- **React**
- **Angular**
- **Svelte**

**Нет** — для управления админкой. Классические формы + серверный рендеринг.

#### Тяжёлые DI-контейнеры

- **Laravel Container**
- **Symfony DI**

**Нет.** Если нужен контейнер — минимальный, свой, 50 строк. И только там, где действительно нужен.

#### AJAX-first архитектура

- **Все модули не строятся вокруг «фронт дёргает API, бэкенд отвечает JSON».**
- **Классические POST-формы + redirect — по умолчанию.**
- **AJAX — только точечно**, где без него UX страдает.

### 12.2. Что разрешено

#### Composer

- **Только для библиотек.** Не для фреймворков.
- Примеры: `monolog/monolog` (PSR-3 логгер), `guzzlehttp/guzzle` (внешние API), `symfony/mailer` (отправка email), `intervention/image` (обработка картинок).
- **PSR-4 автозагрузка** — да.

#### Типизация PHP 8.4+

- `readonly`, `enums`, `attributes`, `declare(strict_types=1)`.
- Типизация аргументов и возвратов — в новом коде.
- **Но не в чанках и не в сниппетах** — там остаётся простой PHP.

#### PDO

- Для нового кода — да.
- Старый `DBAPI` (mysqli) остаётся для extras.

#### Минимальный AJAX

- **Автокомплит живого поиска** — да (нельзя иначе).
- **Галерея в админке** — да (загрузка, drag&drop, инлайн-редактирование).
- **Живой предпросмотр** — да.
- **Всё остальное** — формы.

#### PSR-интерфейсы — точечно

- **PSR-3** (логирование) — для нового кода.
- **PSR-11** (контейнер) — минимальный свой, если понадобится.
- **PSR-14** (event dispatcher) — новый слой (старый `invokeEvent` остаётся).
- **PSR-7** (HTTP) — для нового API.
- **PSR-15** (middleware) — для нового роутинга.

Без фанатизма. Только там, где реально нужно.

### 12.3. AJAX-политика — уточнение (11.10.2026)

**Изначально было:** «AJAX — плохо, везде классические формы».

**Стало:** AJAX **оправдан**, когда без него UX страдает.

#### AJAX оправдан

| Задача | Почему |
|---|---|
| **Живой поиск** (автокомплит) | Без AJAX невозможен |
| **Галерея в админке** (SimpleGallery) | Загрузка, сортировка drag&drop, инлайн-редактирование, модалка «more». Без AJAX UX разрушается |
| **Живой предпросмотр** | Без AJAX невозможен |
| **Внешние API** (SimpleTube → YouTube/VK) | Видео подгружается с внешних сервисов, без AJAX невозможно |

#### AJAX не нужен

| Задача | Почему |
|---|---|
| **Комментарии** | Классическая форма + redirect. Проще, надёжнее |
| **Авторизация** | POST + redirect. OAuth — через редирект |
| **Магазин: корзина** | Сессия |
| **Магазин: оформление** | POST + redirect. Гость + залогиненный |
| **Обычные формы** | POST + redirect |

#### Что это значит для SimpleGallery

**Переписывать под классические формы — НЕ будем.** Пользователь подтвердил: UX удобен, нужен такой же.

**Что делаем:**
- **SchemaGuard** — решает проблему с таблицами (этап 0.3 roadmap).
- **CSRF-JS** — уже починен 11.10.2026 (см. `CHANGELOG-19`).
- **PHP 8.5 warnings** — точечно, по факту.
- **Форк пакета** — позже, внутри `vololution/packages`, для полного контроля.

**Что не делаем:**
- Не переписываем AJAX на формы.
- Не заменяем jQuery на fetch (не срочно).
- Не ломаем UX.

#### Что это значит для SimpleTube

**Не переписываем.** AJAX к API YouTube/VK — не «архитектурный изъян», а необходимость. Видео подгружается с внешних сервисов.

#### Провальный опыт

При обсуждении SimpleGallery в этой сессии я сначала предложил переписать под классические формы. Пользователь возразил: «Мне нужен такой же функционал. Он очень удобен».

**Урок:** не ломать работающее ради «чистоты философии». AJAX — инструмент. Использовать там, где нужно.

### 12.4. Что это значит на практике

**Для разработчика:**

| Задача | Как делает |
|---|---|
| Написать сниппет | PHP-файл, `$modx->db->query(...)`. Как в Evo 2010-х |
| Написать модуль | PHP-файл в `assets/modules/`. Как в Evo |
| Написать плагин | Подписывается на события. Как в Evo |
| Добавить шаблон | Чанк с `[+placeholder+]`. Как в Evo |

**Для системы:**

- Новый код (`src/`) — типизирован, PSR-4, PDO, PSR-3.
- Старый API Evo — работает. Обратная совместимость.
- Постепенно старые модули переписываются на новый слой. Не через «фреймворк», а через нормальный PHP.

**Для фронта:**

| Задача | Решение |
|---|---|
| Комментарии | POST-форма + redirect. Работает без JS |
| Авторизация | POST-форма + redirect. OAuth — через редирект |
| Магазин: корзина | Сессия |
| Магазин: оформление | POST + redirect. Гость + залогиненный |
| Поиск: страница результатов | Обычный GET |
| Поиск: автокомплит | AJAX |
| Галерея в админке | AJAX (оправдан) |

### 12.5. Модернизация extras

Дополнения переписываются **под эту философию**:

- Где классические формы лучше — простые формы.
- Где AJAX оправдан — AJAX остаётся.
- Минимум JS — но не в ущерб UX.
- **Работает без JS — приветствуется там, где возможно.**

**Магазин — перепишем с нуля** под эти принципы. Корзина в сессии, оформление POST + redirect, без AJAX-first.

**SimpleGallery — не переписываем.** UX устраивает.

**SimpleTube — не переписываем.** AJAX к API обоснован.

### 12.6. Куда развивается проект

**Было в старой модели:** «превратить Evo во что-то другое».

**Стало:** «модернизировать Evo, оставаясь Evo».

**Ключевая идея:** простота — это фича, не баг. Разработчик приходит, читает сниппет — понимает. Плагин — понимает. Чанк — понимает. Это не сломать.

### 12.7. Что делать, если соблазн «сделать красиво»

Если очень хочется «правильно» (DI, сервисы, репозитории, DTO) — **сначала спросить: где будет жить этот код?**

- В `src/` — можно. Но не трогает старый API Evo.
- В сниппете — **нельзя**. Сниппет остаётся простым.
- В плагине — **нельзя**. Плагин остаётся простым.
- В модуле — **можно частично**: точка входа простая (`include`), но классы внутри могут быть нормальными.

### 12.8. Если соблазн «убрать AJAX»

Если хочется переписать что-то с AJAX на формы — **сначала спросить: выиграет ли UX?**

- Если UX ухудшится — **не делать.** Простота для пользователя важнее «чистоты».
- Если UX не изменится — можно.
- Если UX улучшится — делать.

**AJAX — не грех. Грех — AJAX ради AJAX.**
